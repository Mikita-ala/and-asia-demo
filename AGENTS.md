## Product rules

- Product language is a permanent UI rule. Every visible string must help a person understand the value of the product or complete their next action. Do not expose implementation details, authorization mechanics, internal roles, server checks, data models, API terminology, or placeholder/demo copy in customer-facing screens.
- Registration and sign-in screens should invite a person into the product, not explain how access is provisioned. Never use copy such as "заявка на доступ", "права доступа", "роль будет назначена", or descriptions of permission checks unless the user explicitly asks for an administrative setting.
- Before shipping a UI change, review all visible copy on the affected screens for technical language and replace it with concise, human product language. Keep this rule in every new screen and state, including empty, loading, error, and mobile views.
- Current phase: build only the Next.js web application with a fully responsive, mobile-first interface. The native Expo/HeroUI application is phase 3 and must not receive product features yet.
- Assume at least 80% of web usage happens on phones. Do not ship desktop-only flows: use touch-first interactions, readable type, no horizontal overflow, and controls with a minimum 44×44 px touch target.
- Validate every web UI change on a narrow phone viewport before desktop refinements. Use browser-responsive layouts; do not use HeroUI Native components for the current web phase.
- Preserve `apps/mobile` as the prepared phase-3 native foundation; change it only when the native stage is explicitly started.
- Keep authorization checks server-side through OpenFGA; never embed OpenFGA credentials or privileged authorization decisions in a client app.
